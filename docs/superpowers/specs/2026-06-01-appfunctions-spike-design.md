# AppFunctions Spike — Expose Billboard Hot 100 #1 to Gemini App

**Date:** 2026-06-01
**Status:** Design — awaiting user review
**Scope:** Test-only spike. Minimum viable surface to verify end-to-end that the Gemini app on a Galaxy S25 can invoke a `@AppFunction` exposed by the Billboard app and receive the current Hot 100 #1 song from our live Retrofit data — including from a cold-started app process.

## Goals (and Non-Goals)

**Goals**
- Expose exactly one `@AppFunction` (`getCurrentHot100TopSong`) from the Billboard app.
- Cold-boot DI works: when the system spawns our process to invoke the function, Hilt provides the existing `:core:domain` UseCase that ultimately calls Retrofit.
- Verify discovery (`adb shell cmd app_function list-app-functions`) and end-to-end invocation from the Gemini app (natural-language query → our function → Gemini-rendered answer).
- One PR, smallest possible diff.

**Non-Goals**
- No ADK integration in this app (Gemini app owns orchestration + Nano).
- No in-app chat UI / no `:feature:agent` module.
- No A2UI renderer.
- No multi-function surface (Top 10, search, collection mutations — all out of scope for the spike).
- No fallback for non-Android-16 devices in this spike — `minSdk` bump is accepted as a known break.

## Verified Facts (from spike research)

- `androidx.appfunctions:1.0.0-alpha09` (May 2026). Three artifacts:
  - `appfunctions` (client)
  - `appfunctions-service` (server-side — what we add)
  - `appfunctions-compiler` (KSP, code-gen)
- `AppFunctionManagerCompat` requires Android 16+ (API 36). Current project `minSdk = 32` → must bump to `36`.
- Provider interface is **`AppFunctionConfiguration.Provider`** (not `AppFunctionFactory.Provider` as the original guide claimed).
- KSP arg `appfunctions:aggregateAppFunctions = true` must be set once at the app module.
- Per-app-function permission for callers: `android.permission.EXECUTE_APP_FUNCTIONS` (Gemini app already holds it).
- Manifest registration is generated by the KSP compiler — no manual `<service>` / `<meta-data>` entry expected for this minimal case.
- Gemini app calling third-party AppFunctions is live in 2026 on Samsung OneUI 8.5+ (S25/S26) and Pixel 9+, but Google describes the developer ecosystem as "a small set of app developers" — automatic discovery by the Gemini app for arbitrary third-party functions is **not guaranteed**. This is the spike's primary unknown.

## Architecture

Single-PR layering, no new modules:

```
:app
  ├── BillboardApplication (existing @HiltAndroidApp)
  │     └─ NEW: implements AppFunctionConfiguration.Provider
  └── appfunctions/
        └─ BillboardFunctions.kt (NEW, @Inject constructor)
              └─ depends on existing :core:domain UseCase

:core:domain
  └── existing GetBillboardHot100UseCase (reused as-is — no new UseCase)
        signature: suspend operator fun invoke(): ChartOverview
        ChartOverview.chartList: List<Chart>  (Chart has rank/title/artist)

:core:data-impl / :core:data-source/prod
  └── existing ChartRepository + Retrofit (reused as-is)
```

Cold-boot flow (verified-by-design, not yet runtime-tested):

```
Gemini app  ──(AppSearch index)──▶  system AppFunction service
                                          │
                                          ▼
                              spawn billboard process (cold)
                                          │
                                          ▼
                       BillboardApplication.onCreate()  ← Hilt graph built
                                          │
                                          ▼
                     appFunctionConfiguration getter invoked
                                          │
                                          ▼
       AppFunctionConfiguration.Builder
         .addEnclosingClassFactory(BillboardFunctions::class.java) { billboardFunctions }
                                          │
                                          ▼
                    generated dispatcher calls BillboardFunctions.getCurrentHot100TopSong(...)
                                          │
                                          ▼
                          GetChartUseCase → ChartRepository → Retrofit
                                          │
                                          ▼
                       TopSong returned ──▶  Gemini app  ──▶  Nano renders answer
```

## Final Outcome — 2026-06-01

### TL;DR

- Provider-side setup is **complete and matches the official `androidx.appfunctions` 1.0.0-alpha09 guide exactly.** No code change needed.
- Gemini app on Galaxy S25 did NOT invoke our function during home test. This is **NOT a bug in our setup.** It is a documented policy gate — see citation below.
- `EXECUTE_APP_FUNCTIONS` is a **caller-side** permission (Gemini, agent apps) — provider apps MUST NOT declare it. Earlier suspicion that we "forgot to register the permission" was incorrect.
- ADK is irrelevant to our app — ADK is for building agents, not for exposing functions. Our spike correctly excluded it.
- Computer Control is a separate framework (OEM-preloaded assistants automating via screenshot analysis). No provider-side action required there either.

### Why Gemini doesn't invoke our function — verbatim citation

From `/ai/appfunctions` (Overview), second paragraph of the body:

> **"As of May 2026, AppFunctions integration with Gemini is in a private preview with trusted testers. You can begin preparing your apps now to use AppFunctions and development tools."**

Combined with the top-of-page experimental banner:

> "**Experimental:** AppFunctions is in an experimental preview as we refine the API surface, and is subject to change."

→ As of 2026-06, third-party AppFunctions are **not** auto-discovered/invoked by the consumer Gemini app outside Google's trusted-tester allowlist. This matches §"Known Risks" row 1 of this spec (predicted at design time, now confirmed by official docs).

### `EXECUTE_APP_FUNCTIONS` permission — clarification

From `/ai/appfunctions` (Overview), body text:

> "...this lets you expose your app's capabilities as orchestratable 'tools' that authorized apps (callers) can discover and execute to fulfill user intents. **Callers must have the `EXECUTE_APP_FUNCTIONS` permission to discover and execute AppFunctions**, and can include agents, apps, and AI assistants like Gemini."

→ This is a **caller-side** permission. The Gemini app (system-preinstalled, privileged) holds it. Our Billboard app (provider) does NOT declare it and MUST NOT. On Android 16 devices, this permission has `protectionLevel="privileged"` so non-system third-party agents can't even acquire it without Instrumentation workaround or priv-app install (per `FilipFan/AppFunctionsPilot` README).

   - `create_note_or_list`, `get_note_or_list`, `update_note_or_list_title`, `add_items_to_list`, `update_list_items`, `clear_list_or_note`

### What is conspicuously absent

> **There is no `invoke_app_function` / `call_app_function` / generic third-party AppFunctions tool in Gemini's client-side catalog.**

The closest entry, `device_actions.open_app(app_name)`, can launch our `MainActivity` but cannot invoke `BillboardFunctions.getCurrentHot100TopSong` or any other AppFunction.

### Implication — this is the OS-level implementation of "private preview with trusted testers"

The 9to5google 2026-02 report stated Gemini *already uses AppFunctions* for Calendar / Notes / Tasks. The presence of `notes_and_lists` in the catalog confirms this — **but it is exposed as a hardcoded, named tool, not as a generic AppFunctions caller.** That is the architectural choice that gates third-party access:

- **Google-owned AppFunctions** → registered in Gemini's tool catalog under a hand-curated name (`notes_and_lists`) → Gemini model knows when to invoke it
- **Third-party AppFunctions** (like ours) → not in the catalog → Gemini model has no symbol to invoke even though the OS has the function indexed and the GSA process holds `EXECUTE_APP_FUNCTIONS=granted=true`

This is the exact technical realization of the "private preview with trusted testers" phrase from `/ai/appfunctions`. Becoming a trusted tester means Google adds an entry to the Gemini tool catalog referencing our function — **no code change on our side will unblock this**.
